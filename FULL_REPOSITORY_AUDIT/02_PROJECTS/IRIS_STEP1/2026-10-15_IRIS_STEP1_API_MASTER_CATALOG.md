### 5.1 Persistence risks from source inspection

- `load_seed_data()` inserts every seed row on each call without a uniqueness/upsert guard. Startup calls `init_db(); load_seed_data()`; `load_seed_data()` itself calls `init_db()`. If seed files contain records, repeated startup may duplicate seed rows. Current seed files for patterns/errors are empty arrays; tools seed contains three rows. Runtime duplicate behavior has not been tested.
- SQLite connection setup sets `row_factory` but the inspected `get_db()` does not explicitly set `PRAGMA foreign_keys=ON`. Foreign-key enforcement therefore must be checked explicitly at runtime rather than assumed.
- No explicit connection timeout, transaction wrapper abstraction, migration framework, backup endpoint, WAL configuration, or database health/restore test was found in the inspected module.
- These are code-review observations, not proof of data loss or runtime failure.

## 6. Task creation, policy, and tool-routing path

Observed path:
1. `POST /projects/{project_id}/tasks` calls `create_task()` from `task_queue.py`.
2. `create_task()` calls `verify_task(project_id, title, phase)`.
3. Verification calls project status, budget and optional phase checks, then queries for duplicate task titles in statuses `COMPLETED`, `RUNNING`, or `QUEUED`.
4. If verification fails, a `ValueError` is raised and endpoint maps it to HTTP 400.
5. If passed, title keywords select `web`, `filesystem`, or `default`; task is inserted as `QUEUED`, audit row `TASK_CREATED` is written, and task ID is returned.

Policy constants observed:
- Active project statuses: `ACTIVE`, `IN_PROGRESS`.
- Allowed phases: `MCR`, `SRR`, `PDR`, `CDR`, `TRR`, `ORR`.
- Queue module declares `MAX_ATTEMPTS = 3`; actual retry/execution behavior is not established by the endpoint source alone.
- `verify_until_clean()` is a local helper loop with a default of 10 rounds; no API route exposing it was found.

Potential implementation issue to test: `create_project_task()` passes a project ID to `create_task`, but `create_task` uses `verify_task`; policy checks are performed before insert. Verify that foreign keys and invalid phase handling behave as intended with real requests.

## 8. API contract standards and engineering requirements

Use the following authoritative standards as reference criteria when reviewing or implementing APIs:

1. **OpenAPI 3.1** — document paths, operations, parameters, request/response schemas, error responses, server URLs, and security schemes. The live generated schema must be fetched and compared with code; a setup note alone is not enough.
2. **HTTP semantics (RFC 9110)** — define method semantics, status codes, caching and idempotency expectations. Avoid retrying non-idempotent create requests blindly; use idempotency keys or deduplication when clients may retry after timeouts.
3. **OAuth 2.0 Security BCP (RFC 9700)** — if OAuth is introduced, use current security practices and avoid deprecated/insecure flows.
4. **OWASP API Security Top 10 (2023)** — review object-level authorization, authentication, property-level authorization, resource consumption, function-level authorization, sensitive business flows, SSRF, misconfiguration, API inventory, and unsafe consumption of upstream APIs.
5. **FastAPI testing guidance** — use TestClient/HTTPX and automated tests for request/response behavior; include positive, negative, authorization, and persistence cases.
6. **SQLite documentation** — verify primary-key behavior, transactions, foreign keys, concurrency, WAL/backup, and recovery against the actual DB configuration.
7. **OpenAI API documentation** — if an OpenAI API integration is later evidenced/authorized, protect API keys server-side, log request IDs and error classes, and handle rate limits/retries; do not assume ChatGPT subscription and OpenAI API billing/access are the same.
